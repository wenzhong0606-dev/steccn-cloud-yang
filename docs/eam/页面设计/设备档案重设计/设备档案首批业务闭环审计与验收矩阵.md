# 设备档案首批业务闭环审计与验收矩阵

日期：2026-10-11。范围：用户PRD基线、当前HTML/控制器/模拟接口、EQ-001当前会话。仅做审计，不修改业务数据或正式数据库。证据分为源码检查、浏览器只读交互、规则测试；未实施不标通过。

## 核心结论

设备档案具备统一入口和21个可访问页签；页签展示检查通过不等于PRD完整或业务闭环通过。当前多数专业领域仅提供样本列表与通用详情。

最优先问题是数据源分裂：archive-api.js读取Eam.s.reports/orders/restrictions/events，而异常事件、故障、维修与隐患的后续模型使用EamProblemApi独立会话。浏览器实证：工单中心显示WO-2001已关闭、WO-2002待技术验收；档案维修页只显示REP-001、REP-002两条历史样本。当前档案不能承担可靠的最新业务汇总。

此前《设备档案跨模块验收矩阵》仍是设计用例。本报告补充实际覆盖，不将其15项用例全部改为通过。25个视图可合并在独立HTML、页签、弹窗中，不能用页签数量判断覆盖率。

## 字段及接口记录修订建议

保留现有《设备档案候选数据关系与接口边界》为设计目标，不把它当已实现字段清单。核心差异：参数当前content文本应映射typed_value/unit/precision/limits；安装需有效期间而非位置文本；状态需专业来源ID与质量时间；维修/故障/限制需权威来源聚合；更换需实例/策略版本/计量基准与证据；审计需source_id/version及字段差异；完整性需适用规则、豁免和修复目标。

候选接口补充（正式API待模型完成后统一）：档案聚合读取需按域调用既有问题/工单/隐患来源并返回source、sourceId、revision、asOf、quality、授权字段；参数修改需字段级校验和影响预览；媒体写操作需统一异步模拟文件接口；安装/更换/保养/绑定/延期属于独立命令，不能伪装为修改通用文本记录。

## 下一批修复边界

第一优先：统一故障/缺陷、维修、隐患/使用限制、概况未结事项、履历的数据源，保留历史样本的来源标签；所有跳转携带实际设备ID、业务对象ID及返回上下文。验收以“新业务结果在档案中正确显示、设备之间不串数据、无权限不泄露、工单验收不自动解除限制”为门槛。

第二优先：参数typed校验/审计、全设备状态能力及完整性修复入口。随后分别实施保养、安装、更换事务；不在一次改造中用更多样本替代这些流程。

本轮未修改业务代码或数据库，不宣称已有86项规则覆盖以上新增缺口；PC逐页签检查并不替代本轮移动交互、角色范围与真实后端验证。
